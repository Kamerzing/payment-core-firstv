# Требования и термины

Исходный план согласован в разговоре с пользователем. Документ фиксирует целевое поведение; фактическая готовность отражается в [progress.md](progress.md).

## Назначение и границы

Учебная система рублёвых кошельков с переводами, комиссиями, резервами и журналом проводок. Средства моделируются; интеграций с банками нет. Первая версия включает Java API, пользовательскую и административную веб-панель, комплект развёртывания на Linux. Публичная регистрация, обмен валют, частичное подтверждение и частичный возврат не входят в первую версию.

Android — отдельный последующий проект на Kotlin и Jetpack Compose. Его авторизация проектируется отдельно. Мобильный клиент использует HTTPS API и не получает доступ к БД или серверным секретам.

## Стек и структура

- Java 21, Spring Boot 4.1.2, Gradle Wrapper с Kotlin DSL; код backend — Java.
- PostgreSQL 18, Spring JDBC с явным SQL, Flyway.
- Spring Security, Spring Session JDBC, Argon2id для паролей.
- springdoc-openapi 3.2.0, JUnit, Spring Boot Test, PostgreSQL Testcontainers.
- React + TypeScript + Vite в отдельной папке репозитория.
- Docker Compose, Caddy, HTTPS; IDE backend — IntelliJ IDEA.
- Модульный монолит: users, wallets, ledger, operations, holds, audit. Все изменения денег выполняются через один механизм проводок.

## Термины и финансовые инварианты

- **Кошелёк:** один RUB-кошелёк на пользователя, с доступным и зарезервированным счетами.
- **Счёт:** участник учёта с производным остатком. Только системный расчётный счёт может иметь отрицательный остаток.
- **Операция:** атомарная группа проводок; у проведённой операции сумма изменений всех счетов равна нулю.
- **Проводка:** неизменяемое изменение счёта. Исправление — новая обратная операция, а не редактирование истории.
- **Резерв:** временное перемещение суммы и комиссии из доступных средств в зарезервированные.
- **Сверка:** пересчёт остатков из журнала и сопоставление с производными остатками и активными резервами.

Суммы в БД — BIGINT в копейках; в Java — long; в JSON — десятичные строки (`amount_minor`). Валюта только RUB. Денежные расчёты не используют float/double. Сложение и вычитание проверяют переполнение, промежуточное умножение для комиссии использует BigInteger.

Остатки и проводки обновляются в одной транзакции. Доступный и зарезервированный остатки, а также счёт комиссий неотрицательны. Учебные пополнения и списания имеют встречную проводку на системном расчётном счёте. БД обеспечивает целостность и запрещает изменение проведённого журнала.

## Пользователи и доступ

- Роли USER и ADMIN; пользователей создаёт администратор.
- Пользователь видит и изменяет только свой кошелёк.
- Администратор создаёт пользователей, пополняет кошельки, выполняет полные возвраты, просматривает аудит и сверку.
- Пароли хешируются Argon2id; первого администратора создаёт отдельная команда без встроенного пароля.
- Для браузера: серверные сессии в PostgreSQL, HttpOnly-cookie, Secure на сервере, CSRF, ограничение попыток входа, завершение сессии при выходе.

Контракт этапа 2: логин из 3–64 ASCII-символов (буквы, цифры, `.`, `_`, `-`, первый — буква или цифра), без учёта регистра; пароль 12–128 символов. API создания назначает USER. Bootstrap ADMIN выполняется отдельной командой ровно один раз. Вход меняет session ID и CSRF; клиент получает новый токен после входа. По умолчанию допускается 5 попыток входа на логин и 30 на адрес соединения за 15 минут, включая успешные; лимиты общие для сессий и сохраняются в БД. Чужой и отсутствующий кошелёк дают одинаковый 404.

Изменение роли или отключение учётной записи учитывается и при уже открытой сессии: управление пользователями повторно проверяет актуальные права, `/auth/me` отклоняет отключённого пользователя.

## Операции и идемпотентность

Пополнение бесплатно. Комиссия перевода и моделируемого списания — 1% сверх суммы, с округлением вверх до копейки. Ставка задаётся конфигурацией и сохраняется вместе с рассчитанной комиссией в операции. Пример: пополнение 1000 ₽, перевод 100 ₽ → 899 ₽ отправителю, 100 ₽ получателю, 1 ₽ счёту комиссий.

Счета блокируются через SELECT … FOR UPDATE в детерминированном порядке. Достаточность средств проверяется после получения блокировок. Любая ошибка отменяет все проводки и изменения остатков.

Каждая денежная команда требует Idempotency-Key, привязанный к действующему пользователю, действию и нормализованному содержимому запроса. Завершённый повтор возвращает сохранённый результат; иной запрос с тем же ключом даёт конфликт. Результат сохраняется атомарно с проводками. Конкурентные повторы должны приводить ровно к одному проведению.

Полный возврат выполняет администратор один раз, включая исходную комиссию. Деньги возвращаются на доступный счёт; резерв не восстанавливается. Недостаток средств на любом счёте обратного движения отменяет возврат целиком.

Контракт этапа 4: ключ имеет область `(actor_id, key)`, хранится бессрочно для успешных команд и сравнивает действие и канонические параметры. Бизнес-ошибки и технические сбои не сохраняются; вся транзакция вместе с ключом откатывается. Повтор после временного сбоя использует прежний ключ. Успешные команды и повторы возвращают 201. Формат ключа: `[A-Za-z0-9][A-Za-z0-9._:-]{0,127}`, ровно один заголовок. Допустимые исходные типы возврата — DEPOSIT, TRANSFER, WITHDRAWAL; возврат возврата запрещён. История пользователя ограничена кошельком, общая история и сверка доступны через admin-маршруты. Списки имеют limit 1–100 и offset >= 0.

Этап 5 расширяет возврат на CAPTURE_TRANSFER и CAPTURE_WITHDRAWAL: обратное движение возвращает сумму и исходную комиссию на доступный счёт без восстановления резерва. Возврат создания, отмены и истечения резерва запрещён.

## Резервирование и предварительный расчёт

Резерв удерживает сумму и комиссию на 15 минут. Состояния: ACTIVE, CAPTURED, CANCELLED, EXPIRED. Подтверждение полное, по сохранённой комиссии; отмена и истечение освобождают всю сумму бесплатно.

Все завершения блокируют одну запись резерва. Срок проверяется по времени БД после получения необходимых блокировок; при expires_at <= текущего времени подтверждать нельзя. Обработчик истечения запускается каждые 30 секунд и обрабатывает накопившиеся резервы после перезапуска.

API расчёта показывает сумму, комиссию и итоговое списание. Денежная команда передаёт подтверждённые условия; backend проверяет их повторно. Изменившийся расчёт требует нового подтверждения пользователя.

POST `/quotes` принимает `type` TRANSFER/WITHDRAWAL и строковый `amount_minor`, возвращает `fee_minor`, `fee_basis_points`, `total_minor` и RUB. Команды передают `expected_fee_minor` и `expected_fee_basis_points`; несовпадение с текущим расчётом — 409 QUOTE_CHANGED. Успешный идемпотентный повтор возвращает сохранённый результат даже после изменения ставки. Quote не сохраняется и не блокирует средства. Числовые JSON-суммы, знак, ведущие нули, дроби и экспонента отклоняются.

`expected_fee_basis_points` передаётся только целым JSON-числом 0–10000. Дробь, экспонента, строка, boolean и переполнение integer отклоняются с 400 INVALID_REQUEST до денежной команды; автоматическое усечение ставки запрещено.

## API и интерфейс

Префикс `/api/v1`. Группы: auth, admin/users, wallets, quotes, transfers, withdrawals, holds, admin/deposits, admin/reversals, admin/audit. Денежные ответы содержат идентификатор, состояние, сумму и комиссию. Списки имеют пагинацию. Внутренние модели хранения не выдаются напрямую.

Ошибки имеют стабильный машинный код и request_id; идентификатор также передаётся заголовком X-Request-ID. Пароли, сессионные идентификаторы и содержимое чувствительных запросов не попадают в журналы.

Пользовательская веб-панель: вход, кошелёк, перевод, списание, резервы, история. Административная: пользователи, пополнения, возвраты, аудит, сверка. Денежная логика и проверка прав остаются на сервере.

Денежная команда требует отдельного подтверждения условий. При неоднозначном сбое ключ и тело сохраняются после перезагрузки вкладки и повторного входа тем же пользователем; ошибки авторизации, CSRF и неизвестные HTTP-ошибки не удаляют запрос. До получения результата новая денежная команда блокируется. Пароли и сессионные данные не записываются в browser storage. Проверяются пользовательские и административные сценарии, мобильная ширина и повтор без двойного списания.

История поддерживает поиск по UUID и просмотр деталей: сумма, комиссия, кошельки, тип, время и исходная операция возврата. Чужая операция скрывается так же, как отсутствующая; административный просмотр использует admin-маршрут.

## Сервер и восстановление

Серверный комплект отделён от локального Compose: Caddy с HTTPS — единственный внешний вход, PostgreSQL и backend без опубликованных портов. Секреты монтируются файлами вне checkout; миграции, runtime и копирование используют раздельные роли БД. Forwarded-заголовки принимаются только от точного адреса Caddy, присланный клиентом адрес не меняет лимит входа. Служебные endpoints закрыты на внешнем прокси.

Копирование выполняется ежедневно в отдельный зашифрованный restic-репозиторий вне сервера. Неуспешный pg_dump не создаёт снимка. Восстановление разрешено только в отдельную пустую БД; после него требуется сверка и проверка ключевых данных. Переключение сохраняет исходный том. Откат приложения возможен только при совместимости прежнего кода с текущей схемой; автоматического понижения схемы или восстановления поверх рабочей БД нет. Инструкция и фактические ограничения: [server.md](server.md).

## Этапы и критерии готовности

1. **Окружение:** три документа контекста; профили local/test/server; PostgreSQL в Docker; Flyway; ошибки и идентификатор запроса; запуск из IDEA и контейнера; локальный Swagger; миграция пустой БД.
2. **Пользователи:** создание пользователей и кошельков, bootstrap администратора, Argon2id, вход/выход, CSRF и ограничение попыток, проверки прав.
3. **Учёт:** счета и проводки, атомарные производные остатки, ограничения и неизменяемость в БД, сверка.
4. **Операции:** пополнение, перевод, списание, комиссия, идемпотентность и полный возврат; контракт предварительного расчёта.
5. **Резервы:** все переходы и обработчик истечения; конкурентное завершение ровно один раз.
6. **Веб-панель:** основные пользовательские и административные сценарии через браузер.
7. **Сервер:** HTTPS, закрытая БД, внешние секреты, ограниченные служебные endpoints, ежедневные внешние резервные копии и проверенное восстановление, процедура обновления и совместимого отката. Фактическое развёртывание требует сервера.

Каждый этап обновляет требования, решения и прогресс. Финансовые тесты выполняются на настоящем PostgreSQL 18 через Testcontainers, включая округление, переполнение, недостаток средств, повторы, конкурентные списания, гонки резервов, откат транзакции, однократный возврат и доступ. Перед серверным выпуском проверяются перезапуск, резервное копирование, восстановление и сценарии веб-панели.
