# Архитектурные решения

## ADR-001. Существующий проект и границы модулей

Сохраняем имя `payment-core2`, group `com.example.payments2` и корневой пакет `com.example.payments2.payment_core2`. Переименование не требуется для реализации плана. Компоненты располагаются под корневым пакетом; общая инфраструктура — common/web и config, предметные пакеты — users, wallets, ledger, operations, holds, audit.

Используем модульный монолит, явный SQL и конструкторное внедрение зависимостей. Веб-контроллеры не проводят операции напрямую; денежные команды вызывают сервисы с транзакционными границами и единый механизм проводок.

## ADR-002. Версии и окружения

Java toolchain 21, Spring Boot 4.1.2, Wrapper 9.8.2 из стартового проекта. Версии Spring, JDBC, Flyway и Testcontainers управляются BOM Spring Boot. springdoc явно закреплён на 3.2.0. PostgreSQL для Compose и тестов — `postgres:18.6-alpine`.

- `local`: импортирует необязательный `.env` из рабочей папки, подключается к локальному PostgreSQL на 5434, разрешает Swagger, слушает loopback.
- `test`: ресурс из src/test/resources; параметры подключения выдаёт Testcontainers через ServiceConnection; БД изолирована от локальных данных.
- `server`: подключение через SPRING_DATASOURCE_URL/USERNAME/PASSWORD, Secure-cookie, Swagger отключён, структурированные ECS-журналы.

Профиль выбирается явно. Пароли не имеют встроенных значений. `.env` и secrets исключены из Git и контекста Docker. Скрипт init-local.ps1 создаёт случайный пароль, сохраняя уже существующий `.env`.

Compose первого этапа предназначен для локальной разработки: порты БД и backend публикуются только на 127.0.0.1. Backend включается профилем Compose `app`, использует профиль Spring `local` и слушает контейнерную сеть. Контейнер работает непривилегированным пользователем, с файловой системой только для чтения и временным /tmp. Серверный Compose с Caddy реализован отдельно в deploy/server (ADR-012). Java-образы закреплены по major 21; перед серверным выпуском проверенные образы закрепляются по digest согласно server.md.

## ADR-003. Схема и сессии

Схема изменяется только Flyway. SQL init и автоматическое создание таблиц Spring Session отключены. Flyway проверяет контрольные суммы, не выполняет baseline автоматически; clean запрещён. V1 создаёт таблицы Spring Session JDBC по совместимому PostgreSQL-формату.

Сессии живут в PostgreSQL, idle timeout 30 минут. Cookie PAYMENT_SESSION: HttpOnly, SameSite=Lax, Secure в server. Используются только cookie, без переноса идентификаторов сессий в URL. CSRF-токен хранится в сессии и выдаётся GET /api/v1/auth/csrf; клиент передаёт token в заголовке header_name. CSRF не отключается для JSON API.

UserDetailsService загружает учётные записи через JDBC. POST /api/v1/auth/login аутентифицирует JSON через DaoAuthenticationProvider, меняет session ID, удаляет прежний CSRF-токен и явно сохраняет SecurityContext в серверной сессии. В сессии остаётся principal с удалёнными credentials. После входа клиент повторно получает CSRF. POST /api/v1/auth/logout очищает CSRF, завершает сессию и удаляет cookie.

Публичны GET status, csrf, минимальные health endpoints, документация в local/test и POST login с обязательным CSRF. Прочие маршруты требуют входа, admin — роль ADMIN. Сохранение неавторизованного запроса, форма входа, HTTP Basic и стандартный logout отключены.

Роль из сохранённого контекста не заменяет проверку актуальной учётной записи. Административные действия, включая создание и список пользователей, повторно проверяют роль и enabled в БД через FinancialAccess. `/auth/me` не возвращает отключённую учётную запись. Изменение роли и отключение при открытой сессии проверяются отдельными HTTP-тестами.

Spring Session и сервисы Testcontainers подключаются через актуальные starter/модули Spring Boot 4, чтобы автоконфигурация была явной. [Spring Session в Boot](https://docs.spring.io/spring-boot/reference/web/spring-session.html), [жизненный цикл Testcontainers](https://docs.spring.io/spring-boot/reference/testing/testcontainers.html).

Явное сохранение контекста и вызов SessionAuthenticationStrategy соответствуют [архитектуре аутентификации Spring Security](https://docs.spring.io/spring-security/reference/servlet/authentication/architecture.html).

## ADR-004. Ошибки и диагностика

Формат ошибки: status, code, message, request_id, timestamp. Ошибки MVC, Security и servlet error dispatch используют один DTO. Сообщения не раскрывают стек, SQL, значения входных полей или внутренние исключения. Подробности validation пока представлены общим INVALID_REQUEST.

X-Request-ID принимается только как единственный заголовок из 1–64 ASCII-символов: первая позиция буква/цифра, далее также `.`, `_`, `-`. При отсутствии, неоднозначности или неверном формате генерируется UUID. Идентификатор находится в заголовке ответа, JSON ошибки и MDC; MDC очищается после запроса. Это диагностический идентификатор, не средство авторизации или идемпотентности.

GET /api/v1/status подтверждает работу HTTP-приложения. Actuator readiness включает проверку БД; liveness от БД не зависит. Публичный health не раскрывает компоненты и параметры подключения. Остальные Actuator endpoints не публикуются.

## ADR-005. Пользователи, кошельки и первый администратор

V2 добавляет app_user, wallet, ledger_account и login_attempt_bucket. UUID создаются приложением. Логины ограничены ASCII, нормализуются через Locale.ROOT и уникальны в БД. Роль хранится в учётной записи; API администратора создаёт только USER. Пароли имеют длину 12–128 символов и хешируются Argon2id: соль 16 байт, хеш 32 байта, память 16384 KiB, 2 прохода, parallelism 1 (defaultsForSpringSecurity_v5_8). Зависимость bcprov-jdk18on закреплена на 1.86; [Spring Security требует Bouncy Castle для этого encoder](https://docs.spring.io/spring-security/reference/7.0/features/authentication/password-storage.html), [дистрибутив Bouncy Castle](https://www.bouncycastle.org/download/bouncy-castle-java/).

UserService создаёт пользователя, один RUB-кошелёк и AVAILABLE/RESERVED счета в одной транзакции. FK, UNIQUE и CHECK запрещают второй кошелёк, неверную валюту, повтор типа счёта и отрицательный остаток, кроме системного SETTLEMENT. FEES и SETTLEMENT создаются миграцией и уникальны по типу. Журнал и команды добавлены миграциями V3/V4.

Чтение кошелька ограничено владельцем в SQL-запросе; это правило действует и для ADMIN. Чужой и неизвестный UUID дают одинаковый 404. Остатки BIGINT преобразуются в строки в API. Списки пользователей используют limit/offset с пределом 100; DTO не содержат паролей и хешей.

Флаг --bootstrap-admin запускает приложение без HTTP, читает пароль через терминальную консоль и закрывает контекст после создания ADMIN. Явный --credentials-stdin разрешает ввод двух строк из защищённого источника. Пароль не принимается аргументом запуска. Транзакционная advisory lock сериализует bootstrap; наличие любого ADMIN запрещает повторное создание. Флаг не запускает bootstrap при обычном старте приложения.

## ADR-006. Ограничение попыток входа

Перед проверкой пароля короткая самостоятельная транзакция резервирует попытку по адресу соединения и нормализованному логину. INSERT ON CONFLICT с условным UPDATE атомарно ограничивает счётчики при параллельных запросах. Лимиты по умолчанию: 30 на адрес и 5 на логин за фиксированное окно 15 минут. Успешные входы также учитываются и не сбрасывают окно. Ошибка аутентификации происходит после коммита счётчиков.

Ключи scope + значение хешируются SHA-256; сроки определяет PostgreSQL через clock_timestamp(). Счётчики общие для экземпляров и сохраняются после перезапуска. Истёкшее окно переоткрывается при следующем запросе; каждые 10 минут задание удаляет до 1000 истёкших строк. В local/test используется адрес соединения; в server Tomcat принимает адрес клиента только от конкретного Caddy (ADR-012).

Неизвестный логин, неверный пароль и отключённая учётная запись получают одинаковый INVALID_CREDENTIALS. Превышение лимита получает LOGIN_RATE_LIMITED. Значения логина и пароля в сообщения об ошибках не включаются; DTO чувствительных запросов имеют скрывающий содержимое toString.

## ADR-007. Неизменяемый журнал и производные остатки

V3 создаёт payment_operation и ledger_posting. Операция создаётся DRAFT и переводится в POSTED в пределах одной транзакции. Отложенный constraint trigger запрещает коммит незавершённой операции, менее двух проводок или ненулевой суммы. Проводка уникальна по паре операция/счёт и не может быть нулевой. Суммирование в PostgreSQL использует NUMERIC; Java проверяет баланс через BigInteger, чтобы порядок сложения не создавал ложное переполнение.

LedgerService работает только внутри существующей транзакции. SELECT FOR UPDATE блокирует все затрагиваемые счета по PostgreSQL UUID-порядку. После блокировки Java проверяет каждый остаток через Math.addExact и достаточность средств. BEFORE INSERT trigger проводки атомарно обновляет баланс; дополнительный отложенный trigger проверяет равенство остатка сумме журнала. Нельзя открыть счёт с ненулевым балансом или поменять его идентичность. V3 отказывается мигрировать необъяснённые ненулевые остатки этапа 2.

UPDATE/DELETE проводок и проведённых операций запрещены триггерами. Добавление проводки блокирует строку операции и разрешено только в DRAFT, поэтому нельзя дописать историю из конкурентного соединения после POSTED. Исправление выполняется отдельной обратной операцией. Ограничения рассчитаны на обычные DML-запросы; владелец схемы способен менять сами ограничения, разделение ролей миграций/приложения относится к серверному этапу.

Сверка выполняется в отдельной read-only транзакции REPEATABLE READ и сопоставляет все остатки, сумму всей системы и баланс каждой операции на одном снимке. Это диагностический отчёт без автоматического ремонта. Начиная с этапа 5 сверка также сопоставляет RESERVED с активными резервами. [Ограничения между строками PostgreSQL](https://www.postgresql.org/docs/18/ddl-constraints.html), [согласованный снимок REPEATABLE READ](https://www.postgresql.org/docs/18/transaction-iso.html).

## ADR-008. Денежные команды, комиссия и возврат

DEPOSIT: SETTLEMENT → AVAILABLE без комиссии. TRANSFER: AVAILABLE отправителя → AVAILABLE получателя и FEES. WITHDRAWAL: AVAILABLE → SETTLEMENT и FEES. Источник всегда определяется текущим пользователем, target_wallet_id передаётся явно; самостоятельный перевод запрещён. Административный список кошельков с фильтром owner_id даёт UUID для пополнения без доступа к БД.

Комиссия в basis points (0–10000, по умолчанию 100) рассчитывается как ceil(amount * bps / 10000), с BigInteger для промежуточного произведения. amount + fee и изменения остатков проверяются на переполнение. Суммы JSON принимаются только десятичными строками целых копеек; специализированный десериализатор запрещает автоматическое преобразование JSON-чисел в строки.

Quote не сохраняется: клиент подтверждает expected_fee_minor и expected_fee_basis_points; команда сверяет их с текущей политикой. Несовпадение даёт QUOTE_CHANGED до проведения. В операции сохраняются фактическая ставка и комиссия. Смена конфигурации не меняет проведённые операции или сохранённый ответ повтора.

StrictIntegerDeserializer принимает expected_fee_basis_points только из целочисленного JSON-токена без преобразования дробей, экспоненты или строк. Диапазон 0–10000 проверяется validation. Правило одинаково для переводов, списаний и создания резервов.

Возврат разрешён только ADMIN для DEPOSIT, TRANSFER, WITHDRAWAL. Строка исходной операции блокируется, уникальная original_operation_id запрещает второй возврат, включая разные ключи. Проводки разворачиваются полностью, по исходной комиссии. Недостаток средств отменяет всю транзакцию; повтор возможен после устранения причины. Возврат возврата запрещён. Денежные сервисы повторно проверяют активность пользователя и роль в БД. На команду задан транзакционный timeout 15 секунд.

## ADR-009. Результат команды, повторы и аудит

V4 создаёт command_result с PRIMARY KEY (actor_id, idempotency_key). Ключ 1–128 ASCII-символов. Fingerprint SHA-256 строится из действия и канонических значений UUID, суммы и подтверждённых условий. INSERT ON CONFLICT DO NOTHING ждёт конкурентную транзакцию: при коммите победителя читается результат, при откате команду выполняет ожидающий запрос. Разные параметры под одним ключом дают IDEMPOTENCY_CONFLICT.

Результат JSON сохраняется в той же транзакции, что проводки и audit_event; отложенная проверка запрещает незаполненный результат при коммите. Успешные результаты неизменяемы и хранятся бессрочно. Бизнес-ошибки и технические сбои не сохраняются: нет ключа без завершённой команды и нет отдельного PROCESSING, требующего восстановления. HTTP-статус денежных команд и повторов фиксирован: 201. Транзиентные ошибки JDBC получают 503 RETRYABLE_FAILURE с инструкцией повторить прежний ключ.

Аудит содержит actor_id, действие, operation_id, request_id и время; не содержит паролей, cookie или тела запроса. UPDATE/DELETE событий запрещены. Повтор не создаёт второе событие. Общий журнал, аудит и сверка доступны только через admin-маршруты; обычная история ограничена владельцем даже для ADMIN.

## ADR-010. Резервы и освобождение средств

V5 добавляет payment_hold со сроком 15 минут и переходом ACTIVE → CAPTURED/CANCELLED/EXPIRED. Создание резервирует сумму и комиссию проводками AVAILABLE → RESERVED; условия сохраняются в резерве. Подтверждение списывает RESERVED получателю/SETTLEMENT и FEES, отмена и истечение возвращают всю сумму в AVAILABLE. Возврат CAPTURE_TRANSFER/CAPTURE_WITHDRAWAL зачисляет средства в AVAILABLE и не восстанавливает резерв. Создание и освобождение резервов не подлежат возврату.

Все завершения блокируют одну строку резерва, затем счета в общем UUID-порядке. Фактическое время БД проверяется после получения всех блокировок; используется clock_timestamp(), поскольку now() фиксирует начало транзакции. Trigger дополнительно запрещает просроченное подтверждение непосредственно при переходе. Завершённый резерв неизменяем; повтор команды использует обычный command_result. [Время транзакции и фактическое время PostgreSQL](https://www.postgresql.org/docs/18/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT).

Блокируются оба счёта каждого затронутого кошелька. Проверяется предел AVAILABLE + RESERVED <= Long.MAX_VALUE, чтобы освобождение любого резерва всегда помещалось на доступном счёте. Отложенные ограничения и сверка сравнивают RESERVED с суммой всех ACTIVE на одном снимке.

Обработчик истечения запускается сразу и каждые 30 секунд, выбирает до 100 просроченных резервов, завершает каждый в отдельной транзакции и пропускает занятые строки через SKIP LOCKED. Незавершённые резервы остаются в БД для следующего запуска, включая перезапуск приложения; отключение владельца не мешает освобождению. Свойство payment.holds.expiration.enabled позволяет отключить задание; в test оно отключено для воспроизводимых проверок.

## ADR-011. Веб-панель и неопределённый результат команды

React/TypeScript/Vite находятся в web/. Gradle собирает панель в static внутри JAR; webTest входит в check/build, Playwright запускается отдельно с изолированным PostgreSQL Testcontainer и тестовым сервером на loopback:18080. Браузер обращается к API того же origin. Серверные HttpOnly-cookie и CSRF защищают команды; пароли, cookie и CSRF не сохраняются в browser storage. CSP разрешает скрипты и стили только с текущего origin.

Суммы вводятся в рублях, преобразуются в строки копеек и форматируются через BigInt. Перед денежной командой пользователь подтверждает отдельное окно с суммой, комиссией и итогом. Клиент сохраняет ключ, тело и описание команды в sessionStorage с привязкой к UUID пользователя до отправки. После потери ответа или перезагрузки вкладки повторяется тот же запрос; новая денежная команда блокируется до разрешения результата.

Ошибки авторизации/CSRF и неизвестные HTTP-ошибки не подтверждают исход предыдущей попытки, поэтому не удаляют сохранённый запрос. После повторного входа тем же пользователем он восстанавливается. Очистка выполняется при успехе или известном бизнес-отказе backend; IDEMPOTENCY_CONFLICT сохраняет исходные данные для выяснения результата. Закрытие вкладки удаляет sessionStorage, поэтому перед новой операцией нужно проверить историю. Браузерные сценарии проверяют потерю ответа после реального коммита, перезагрузку, CSRF-отказ, истечение сессии и однократное списание с исходным ключом.

История открывает подробности операции по UUID через собственный или административный GET-маршрут. Данные не берутся из изменяемых полей формы, повторно проверяются backend. Окно поддерживает загрузку, повтор при сбое и закрытие с клавиатуры; обычный пользователь не видит чужие операции. Денежные суммы форматируются прежним точным механизмом.

Общий useRemote связывает полученные данные с URL. Сбой следующей страницы не отображает предыдущую страницу под новым номером; повтор загружает нужный URL. Обновление того же URL сохраняет последний успешный результат.

## ADR-012. Серверная сеть, роли и обслуживание

Серверный Compose отделён от локального. Единственный внешний вход — Caddy на TCP 80/443; proxy и database — внутренние сети. Caddy и backend имеют разные фиксированные адреса во внутренней proxy-сети; это исключает конфликт при последовательном старте. Tomcat native forwarding доверяет только адресу Caddy с маской /32. Прокси заменяет X-Forwarded-For адресом соединения, удаляет Forwarded, закрывает Actuator/OpenAPI/Swagger и ограничивает тело запроса. CSP и защита cookie остаются у backend. [Заголовки Caddy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#headers), [настройки Spring Boot](https://docs.spring.io/spring-boot/appendix/application-properties/index.html).

PostgreSQL создаёт отдельные payment_migrator, payment_app и payment_backup. Владелец схемы запускает миграции отдельной командой --migrate-only и завершается до backend. Runtime работает с DML-правами без CREATE/TRUNCATE/возможности менять триггеры. Backup имеет только чтение. Пароли передаются файловыми Compose secrets; приложение читает пароль через configtree. Backend и maintenance не получают пароль владельца схемы. Инициализация ролей выполняется только на пустом томе. [Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/).

Команды --migrate-only, --reconcile-only и bootstrap запускаются без HTTP и закрывают контекст. Maintenance имеет только database-сеть и динамический адрес, поэтому запуск рядом с backend не повторяет его фиксированный proxy-адрес. --reconcile-only возвращает ненулевой код при расхождении. Runtime не запускает Flyway. Контейнеры работают с read-only rootfs, ограничениями памяти/процессов и сброшенными capabilities; краткий root volume-init меняет только владельцев корней именованных томов. Серверный образ из проверенного JAR не требует компиляции на сервере.

## ADR-013. Копирование, восстановление и откат

Restic получает custom archive pg_dump PostgreSQL 18 через --stdin-from-command: сбой команды не создаёт снимок. Репозиторий отдельный для окружения, зашифрован и находится вне сервера; пароль и параметры доступа монтируются отдельно. После копии выполняется restic check, удерживаются 14 daily / 8 weekly / 12 monthly снимков. Systemd timer запускает копию ежедневно; оператор подключает мониторинг неуспешных запусков. Полный read-data check и тренировка восстановления выполняются отдельно. [Обработка exit code дампа](https://restic.readthedocs.io/en/stable/040_backup.html#reading-data-from-a-command).

Restore жёстко ограничен отдельным сервисом restore-postgres и пустой payment_restore, выполняется одной транзакцией. Проверка требует совпадения журнала, остатков и ACTIVE-резервов, а также сверки ключевых данных. Переключение через promote-restored.yaml монтирует проверенный том к основному postgres после остановки обоих процессов; исходный том сохраняется. Восстановленные сессии удаляются до открытия доступа, ключи денежных команд сохраняются.

Перед обновлением нужна свежая внешняя копия и проверка восстановления. Миграции следуют expand/contract; бинарный откат допустим только при совместимости старого кода с новой схемой. Автоматического понижения схемы или отката БД поверх рабочей базы нет. Серверный drill проверяет комплект в отдельном Docker-проекте; публичный сертификат, реальное внешнее хранилище и systemd требуют проверки на фактическом сервере. Процедуры: [server.md](server.md).
