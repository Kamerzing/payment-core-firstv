## Найденные и исправленные ошибки

### Права старой административной сессии

`AdminUserController` проверял только роль, сохранённую при входе. После изменения роли ADMIN → USER в БД уже открытая сессия продолжала создавать пользователей и получать их список. Отключение пользователя также не учитывалось в `/auth/me`.

Добавлена проверка `FinancialAccess.actor(..., true)` перед обеими административными командами, как у остальных admin-маршрутов. Загрузка текущего пользователя исключает `enabled=false`. После снятия роли управление пользователями возвращает 403; после отключения `/auth/me` и управление пользователями возвращают 401. Запрещённое создание не оставляет пользователя или кошелёк.

Два новых HTTP-теста сначала воспроизвели ошибку на исходном коде, затем прошли после исправления: `deniesUserAdministrationAfterRoleChangesInAnExistingSession` и `deniesDisabledAdministratorWithAnExistingSession`. Механизм сохранения контекста описан в [Spring Security](https://docs.spring.io/spring-security/reference/servlet/authentication/persistence.html); актуальное состояние учётной записи проверяется приложением дополнительно.

### Предыдущая страница под новым номером

`useRemote` сохранял результат предыдущего URL при смене страницы. Если запрос следующей страницы завершался ошибкой, история могла показать прежние операции под новым диапазоном записей. Общий hook используется также списками резервов, пользователей, кошельков и аудита.

Результат теперь связан с URL запроса: данные другого URL не отображаются. Пустой pager показывает «Нет загруженных записей». Новый браузерный сценарий воспроизвёл старую ошибку, затем проверил её исправление и успешную повторную загрузку нужной страницы. Кэш того же URL сохраняется при обычном обновлении.

### Устаревший синтаксис Gradle

Задачи `webInstall`, `webBuild`, `webTest` переведены с устаревшего delegated `registering(Exec::class)` на `register<Exec>`. Устранено предупреждение об удалении этого синтаксиса в Gradle 10 без изменения поведения задач.

### Автоматическое преобразование ставки комиссии

Разбор JSON преобразовывал дробное `expected_fee_basis_points: 100.9` в целое `100` и допускал команду. Контракт требует целое JSON-число: параметры подтверждения не должны округляться при разборе.

`StrictIntegerDeserializer` принимает только целочисленный JSON-токен; границы 0–10000 проверяются прежними validation-ограничениями. Применён к переводу, списанию и созданию резерва. Тест `rejectsFractionalAndCoercedFeeRatesWithoutChangingMoney` сначала воспроизвёл ошибку, затем проверил 24 отказа: дробь, экспонента, строка, переполнение integer, null, boolean и выход за границы для трёх маршрутов. Остатки, операции, результаты команд и резервы при отказах не изменяются.

Миграции V1–V5 и финансовые правила при этих исправлениях не изменялись.

## Готовность первой версии

Функциональность первой учебной версии реализована. После исправлений проект подходит для локальной демонстрации и ограниченного пилота с моделируемыми средствами. По проверенным сценариям блокирующих дефектов финансового ядра не обнаружено.

Серверный выпуск пока не завершён: нет предоставленного целевого сервера, домена и внешнего хранилища. Локальная проверка контейнеров не подтверждает публичный DNS/сертификат, фактическое расписание systemd, внешнюю копию и время аварийного восстановления в целевой среде. До объявления серверного релиза нужно пройти эти пункты по [server.md](server.md), закрепить проверенные образы по digest, зафиксировать исходники и тег выпуска.

Проверена функциональная корректность, включая отдельные конкурентные сценарии. Предельная производительность и длительная работа под нагрузкой не измерялись. Текущий server Compose рассчитан на один сервер; остановка при обновлении допустима, отказоустойчивого кластера нет. Ежедневный дамп не сохраняет операции после последнего снимка; допустимую потерю данных и время восстановления нужно определить для пилота.

Ключи успешных команд и финансовая история сохраняются бессрочно. Вкладка хранит неопределённый запрос в `sessionStorage`; закрытие вкладки требует проверки истории перед новой командой. Android и банковские интеграции не входят в объём первой версии.

## Дальнейшая разработка

1. **Завершить серверный выпуск.** Развернуть проверенный образ, проверить публичный HTTPS, внешнюю копию и восстановление; включить timer и уведомления об ошибках копирования, нехватке диска и недоступности приложения. Зафиксировать время восстановления и допустимый интервал потери данных.
2. **Автоматизировать выпуск и сопровождение.** CI с Gradle, Playwright и серверным сценарием; проверка Java/npm/container-зависимостей, сохранение артефактов и digest, порядок обновления и регулярные тренировки восстановления. Провайдер CI выбирается вместе с удалённым Git-репозиторием.
3. **Добавить жизненный цикл учётных записей.** Смена пароля, управляемое завершение сессий, отключение пользователя через admin UI и аудит действий доступа. Сейчас пользователей создаёт администратор, отдельного интерфейса для смены пароля и отключения нет.
4. **Развивать работу с историей и измерить нагрузку.** Фильтры/экспорт, понятное направление движения денег; нагрузочный стенд с растущим журналом. В первую очередь измерить общие блокировки системных счетов, пересчёт журнала в deferred-триггерах, полную сверку и offset-пагинацию. Индексы и изменения алгоритмов добавлять по результатам измерений, сохраняя финансовые инварианты.
5. **Разработать Android-клиент отдельным этапом.** Согласовать мобильную авторизацию и хранение учётных данных, использовать существующий HTTPS API и сохранять ключи денежных команд до определённого результата. Денежная логика остаётся в backend.

Модульный монолит подходит текущему объёму: транзакции денег, ключей и аудита остаются в одной PostgreSQL. Решение о разделении сервисов имеет смысл принимать после появления измеренной нагрузки или независимых требований к эксплуатации модулей.
