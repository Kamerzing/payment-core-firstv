# Payment Core

Учебное платёжное ядро на Java 21 / Spring Boot 4.1.2 с веб-панелью React / TypeScript. Реализованы пользователи, RUB-кошельки, неизменяемые проводки, денежные команды, возвраты, резервы, аудит и сверка. Средства моделируются, интеграций с банками нет.

Контекст проекта: [требования](docs/requirements.md), [решения](docs/architecture.md), [прогресс](docs/progress.md).

Проверка всех семи этапов, исправления, оценка готовности первой версии и дальнейший план: [готовность выпуска](docs/release-readiness.md).

Серверный Compose с Caddy/HTTPS, раздельными ролями БД, внешними секретами, restic и восстановлением: [инструкция сервера](docs/server.md).

## Локальный запуск на Windows

Нужны JDK 21, Node.js 22.12+ с npm и работающий Docker Desktop с Linux containers. Отдельный Gradle не требуется. Все команды выполняются из корня проекта. Gradle автоматически устанавливает зависимости панели через `npm ci`, собирает её и включает в JAR.

```powershell
$env:JAVA_HOME='C:\Program Files\Java\jdk-21.0.12.1'
$env:PATH=$env:JAVA_HOME+'\bin;'+$env:PATH
.\scripts\init-local.ps1
docker compose up -d --wait postgres
.\gradlew.bat bootRun --args="--spring.profiles.active=local"
```

Скрипт создаёт `.env` со случайным паролем, если файла ещё нет. Этот файл не коммитится и не попадает в Docker-образ. Альтернатива: скопировать `.env.example` в `.env` и задать собственный POSTGRES_PASSWORD. В `.env` можно поменять DB_PORT (5434) и APP_PORT (8080). Изменение пароля в файле не меняет пароль в уже созданной БД.

В IntelliJ IDEA установить Project SDK = 21, Gradle JVM = 21; в конфигурации запуска PaymentCore2Application задать `SPRING_PROFILES_ACTIVE=local` и рабочую папку корня проекта. При этих настройках приложение прочитает тот же `.env`.

После запуска:

- [Веб-панель](http://localhost:8080/)
- [Swagger UI](http://localhost:8080/swagger-ui/index.html)
- [OpenAPI](http://localhost:8080/v3/api-docs)
- [HTTP status](http://localhost:8080/api/v1/status)
- [Readiness приложения и БД](http://localhost:8080/actuator/health/readiness)
- [Liveness](http://localhost:8080/actuator/health/liveness)

`GET /api/v1/auth/csrf` возвращает token и header_name и устанавливает HttpOnly-cookie PAYMENT_SESSION. Изменяющие запросы, включая вход и выход, требуют cookie и токен в указанном заголовке. Закрытые маршруты без входа возвращают 401, запрос без CSRF — 403.

## Первый администратор

При работающей локальной БД выполнить из терминала с JDK 21:

```powershell
.\gradlew.bat bootJar
java -jar build/libs/payment-core.jar --bootstrap-admin --spring.profiles.active=local
```

Команда запрашивает логин, пароль и подтверждение; пароль не отображается. Она применяет миграции, создаёт администратора вместе с кошельком и завершает работу без HTTP-сервера. Повторный bootstrap при существующем ADMIN завершается ошибкой; одновременные запуски создают одного администратора. Встроенного пароля и публичной регистрации нет.

Логин: 3–64 символа ASCII, буквы, цифры, `.`, `_`, `-`, первый символ — буква или цифра. Логины приводятся к нижнему регистру. Пароль: 12–128 символов, хранится как Argon2id с индивидуальной солью.

Для автоматизации есть явный флаг `--credentials-stdin`: первые две строки стандартного ввода — логин и пароль. Передавайте их из защищённого источника; пароль не передаётся аргументом командной строки. Для server-профиля параметры БД передаются через окружение, как при обычном запуске.

## Пользователи, вход и кошелёк

| Метод | Путь | Доступ и результат |
| --- | --- | --- |
| GET | `/api/v1/auth/csrf` | CSRF-токен и сессионная cookie |
| POST | `/api/v1/auth/login` | JSON `username`, `password`; данные вошедшего пользователя |
| GET | `/api/v1/auth/me` | Текущий пользователь |
| POST | `/api/v1/auth/logout` | Завершение сессии, 204 |
| POST | `/api/v1/admin/users` | ADMIN: JSON `username`, `password`; создание USER, 201 |
| GET | `/api/v1/admin/users?limit=20&offset=0` | ADMIN: `items`, `limit`, `offset`; limit 1–100 |
| GET | `/api/v1/wallets/me` | Свой кошелёк |
| GET | `/api/v1/wallets/{id}` | Свой кошелёк по UUID; чужой и отсутствующий дают 404 |

Последовательность клиента: получить CSRF и cookie, выполнить login с ними, сохранить новую cookie, снова получить CSRF, затем отправлять изменяющие запросы. При входе идентификатор сессии и CSRF-токен меняются. После logout прежняя cookie больше не даёт доступ.

Создание пользователя атомарно создаёт один RUB-кошелёк и два счёта с нулевыми остатками. API создания всегда назначает USER; ADMIN создаётся отдельной командой. Пароли и хеши не выдаются API. Администратор тоже читает через `/wallets` только собственный кошелёк. Остатки в JSON — строки копеек: `available_minor: "0"`, `reserved_minor: "0"`.

Лимит входа: 5 допущенных попыток на логин и 30 на адрес за окно 15 минут. Считаются успешные и неуспешные попытки; новый браузер и изменение регистра логина не сбрасывают лимит. Счётчики хранятся в PostgreSQL, истёкшие окна переоткрываются при запросе и очищаются фоновым заданием. Превышение возвращает 429 `LOGIN_RATE_LIMITED`; неизвестный пользователь, неверный пароль и отключённая учётная запись — одинаковый 401 `INVALID_CREDENTIALS`.

Настройки: `payment.security.login.account-limit`, `payment.security.login.address-limit`, `payment.security.login.window`. Адрес берётся из соединения; произвольный X-Forwarded-For не принимается. Настройка доверенного прокси относится к серверному этапу.

Пример ошибки:

```json
{
  "status": 401,
  "code": "UNAUTHORIZED",
  "message": "Authentication is required.",
  "request_id": "example-request-1",
  "timestamp": "2026-10-28T00:00:00Z"
}
```

## Денежные команды и история

Все пути ниже имеют префикс `/api/v1`. Денежные POST требуют входа, CSRF и **одного** заголовка `Idempotency-Key`: 1–128 ASCII-символов, первый — буква/цифра, остальные также `.`, `_`, `:`, `-`. Для новой команды создавайте новый ключ; после потери ответа повторяйте прежний ключ и тело.

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/quotes` | Расчёт комиссии: `type` TRANSFER/WITHDRAWAL, `amount_minor` |
| POST | `/admin/deposits` | ADMIN: `wallet_id`, `amount_minor`; пополнение без комиссии |
| GET | `/admin/wallets?owner_id={user_id}` | ADMIN: кошельки, фильтр по UUID пользователя необязателен |
| POST | `/transfers` | Свой кошелёк → `target_wallet_id`; сумма и подтверждённая комиссия |
| POST | `/withdrawals` | Списание со своего кошелька; сумма и подтверждённая комиссия |
| POST | `/admin/reversals` | ADMIN: `operation_id`; полный возврат, включая исходную комиссию |
| GET | `/operations`, `/operations/{id}` | Своя история и операция; чужая и неизвестная дают 404 |
| GET | `/admin/operations`, `/admin/operations/{id}` | ADMIN: общий журнал |
| GET | `/admin/audit` | ADMIN: события успешных денежных команд и request_id |
| GET | `/admin/reconciliation` | ADMIN: сверка журнала и остатков на одном снимке БД |

Списки возвращают `items`, `limit`, `offset`; значения по умолчанию 20/0, limit 1–100. Обычный `/operations` ограничен собственными операциями даже для ADMIN. Пополнение и перевод принимаются только для существующего активного получателя; перевод самому себе запрещён.

Пример предварительного расчёта:

```json
{"type":"TRANSFER","amount_minor":"10000"}
```

Ответ: `currency: "RUB"`, `amount_minor: "10000"`, `fee_minor: "100"`, `fee_basis_points: 100`, `total_minor: "10100"`. После подтверждения пользователем отправляется перевод:

```json
{
  "target_wallet_id": "UUID кошелька получателя",
  "amount_minor": "10000",
  "expected_fee_minor": "100",
  "expected_fee_basis_points": 100
}
```

Для списания используются те же поля без `target_wallet_id`. Quote не резервирует деньги и не требует Idempotency-Key. Команда повторно проверяет ставку и комиссию; `409 QUOTE_CHANGED` требует нового расчёта и подтверждения. Настройка `payment.fees.basis-points` задаёт ставку от 0 до 10000; по умолчанию 100 = 1%, комиссия начисляется сверх суммы и округляется вверх до копейки. Ставка и комиссия сохраняются в операции.

Суммы передаются **строками целого числа копеек** без знака, пробелов, ведущих нулей, дробей и экспоненты. Числовые JSON-значения отклоняются. Положительная сумма ограничена Java long; сумма с комиссией и каждый получившийся остаток проверяются на переполнение. Денежная команда возвращает 201, UUID операции, `state: "POSTED"`, тип, кошельки, строковые сумму/комиссию/итог, ставку и время.

Идемпотентность имеет область `(пользователь, ключ)` и сравнивает действие и нормализованные параметры. Успешный повтор возвращает сохранённый ответ с тем же статусом 201; изменение действия, получателя, суммы или подтверждённых условий даёт `409 IDEMPOTENCY_CONFLICT`. Параллельные повторы проводят деньги один раз. Ключи успешных команд хранятся бессрочно. Бизнес-ошибки и технические сбои откатывают транзакцию вместе с ключом: после исправления причины можно повторить тот же запрос. При `503 RETRYABLE_FAILURE` повторяйте с тем же ключом. Нехватка средств — `409 INSUFFICIENT_FUNDS`, переполнение остатка — `409 BALANCE_OVERFLOW`.

Возврат разрешён для DEPOSIT, TRANSFER, WITHDRAWAL, CAPTURE_TRANSFER и CAPTURE_WITHDRAWAL ровно один раз; новая обратная операция не меняет исходную историю. Возврат возврата и возврат создания/освобождения резерва запрещены. Если получатель уже потратил деньги либо средств на другом списываемом счёте недостаточно, весь возврат отклоняется. Возврат подтверждённого резерва зачисляется в AVAILABLE и не открывает резерв повторно.

PostgreSQL применяет проводки к остаткам в той же транзакции. Отложенные ограничения проверяют баланс операции и равенство остатка журналу. UPDATE/DELETE проводок и проведённых операций, а также добавление к ним проводок запрещены. Счета блокируются по UUID в едином порядке. Сверка использует REPEATABLE READ и ничего не исправляет автоматически; `consistent: false` требует расследования.

## Резервы

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/api/v1/holds` | Создать резерв TRANSFER/WITHDRAWAL |
| GET | `/api/v1/holds?limit=20&offset=0` | Свои резервы с пагинацией |
| GET | `/api/v1/holds/{id}` | Свой резерв; чужой и отсутствующий дают 404 |
| POST | `/api/v1/holds/{id}/capture` | Полностью подтвердить по сохранённой комиссии |
| POST | `/api/v1/holds/{id}/cancel` | Бесплатно освободить удержанную сумму и комиссию |

Денежные POST требуют CSRF и Idempotency-Key; успешный ответ и повтор — 201. Создание принимает `type`, `amount_minor`, `expected_fee_minor`, `expected_fee_basis_points`; для TRANSFER обязателен `target_wallet_id`, для WITHDRAWAL он отсутствует. Комиссию сначала получите через `/quotes`. Завершения принимают пустое JSON-тело `{}`. Ответ содержит UUID резерва, состояние, сохранённые условия, `expires_at`, `creation_operation_id` и `completion_operation_id`.

Создание переводит сумму + комиссию из AVAILABLE в RESERVED на 15 минут по времени PostgreSQL. Подтверждение переводит деньги из RESERVED получателю/SETTLEMENT и FEES; отмена и истечение возвращают всю сумму в AVAILABLE. Изменение тарифа не меняет условия резерва. Состояния: ACTIVE → CAPTURED/CANCELLED/EXPIRED, один терминальный переход. Другой ключ после завершения получает 409 HOLD_CLOSED, прежний ключ возвращает сохранённый ответ. Просроченное подтверждение получает 409 HOLD_EXPIRED; отмена просроченного резерва освобождает его со статусом EXPIRED.

Все завершения блокируют резерв, затем оба счёта каждого затрагиваемого кошелька в общем UUID-порядке и проверяют `clock_timestamp()` после блокировок. Проверка срока есть и в trigger финального перехода. Общий остаток AVAILABLE + RESERVED не может превысить long: пополнение не должно лишить кошелёк возможности освободить резерв. БД и сверка сравнивают RESERVED с суммой ACTIVE.

Фоновое задание включено по умолчанию: сразу после запуска и каждые 30 секунд обрабатывает до 100 просроченных резервов. Каждое завершение имеет отдельную транзакцию, SKIP LOCKED допускает несколько экземпляров; ошибка одного резерва не откатывает остальные. После перезапуска состояние восстанавливается из БД. Отключённый владелец не препятствует автоматическому освобождению. В тестовом профиле автоматический запуск отключён через `payment.holds.expiration.enabled=false`.

## Веб-панель

В собранном JAR панель открывается на `/`, API использует тот же origin и серверные cookie. Введите учётную запись, созданную администратором. Пользователь видит остатки, свой номер кошелька, формы перевода и списания, резервы и историю. ADMIN дополнительно видит создание пользователей, список кошельков с именами владельцев, пополнения, полные возвраты, общий журнал, аудит и сверку. Основные экраны адаптированы для телефона.

В истории можно открыть операцию нажатием на её название или найти её по UUID. Подробности показывают сумму, комиссию, кошельки и исходную операцию возврата; пользователь видит только собственные операции, административный журнал использует отдельные права. При сбое загрузки доступны повтор и закрытие окна. [Мобильный экран деталей](docs/screenshots/operation-details-mobile.png).

Перед денежной командой показывается отдельное окно с получателем, суммой, комиссией и итогом. До подтверждения деньги не меняются. После отправки ключ и тело запроса сохраняются в sessionStorage с привязкой к пользователю; при потере ответа кнопка «Проверить результат» повторяет тот же запрос, в том числе после перезагрузки этой вкладки. Новая денежная команда до разрешения неопределённого результата не создаётся. Пароль, session ID и CSRF в браузерное хранилище не записываются. sessionStorage сохраняется только в текущей вкладке: после её закрытия проверьте историю перед повторным созданием операции.

Ошибка авторизации, CSRF, ограничения запросов или промежуточного сервера сохраняет незавершённый запрос. После истечения сессии войдите тем же пользователем в той же вкладке и нажмите «Проверить результат»: клиент использует исходный ключ. Сохранённый запрос удаляется после успешного ответа либо известной бизнес-ошибки, подтверждающей отказ команды.

Для разработки интерфейса запустите backend с local-профилем, затем в другом терминале:

```powershell
cd web
npm ci
npm run dev
```

Vite доступен на http://127.0.0.1:5173 и передаёт `/api` в backend на http://127.0.0.1:8080. Для другого адреса задайте `API_TARGET`. Сборка отдельно: `npm run build`. В обычном `bootJar`/`build` панель собирается автоматически. В Docker используется отдельная стадия Node 24, runtime содержит только Java. `-PskipWebBuild` предназначен для уже собранного `web/dist`, как в Docker; при его отсутствии сборка завершается ошибкой.

Скриншоты тестовых данных: [кошелёк](docs/screenshots/wallet-desktop.png), [телефон](docs/screenshots/wallet-mobile.png), [сверка администратора](docs/screenshots/admin-reconciliation.png).

## Запуск приложения в контейнере

Остановить локальное приложение, если оно занимает 8080, затем:

```powershell
docker compose --profile app up -d --build --wait
docker compose ps
docker compose logs backend
```

Образ собирается из исходников через Wrapper, запускается на Java 21 от непривилегированного пользователя. PostgreSQL и backend доступны с хоста только через loopback. Данные сохраняются в именованном Docker-томе.

```powershell
docker compose --profile app stop
```

Эта команда останавливает контейнеры и сохраняет БД. Локальный Compose использует HTTP и профиль local; отдельный [серверный комплект](docs/server.md) использует HTTPS и профиль server.

## Проверки

```powershell
.\gradlew.bat classes
.\gradlew.bat test
.\gradlew.bat clean build
```

`build`/`check` также запускают модульные тесты интерфейса задачей `webTest`. `npm test` проверяет файлы в `web/src`; браузерные сценарии запускаются отдельно через `npm run test:e2e`.

Тесты автоматически создают отдельные контейнеры PostgreSQL 18 и применяют Flyway к пустой БД; `.env` и запущенная локальная БД им не нужны. Проверяются обновление V1 до текущей схемы с сохранением сессий, bootstrap из собранного JAR, вход/выход, cookie/CSRF, права и лимиты. Финансовые тесты проверяют округление, переполнение, повторы, конкурентные списания и переводы, однократный полный возврат, откат при сбое после проведения, защиту журнала и сверку во время конкурентных команд. Задача test собирает bootJar для проверки команды администратора. Docker необходим, без него тесты завершаются ошибкой, а не пропускаются. Отчёт: `build/reports/tests/test/index.html`. На Linux/macOS используются те же команды через `./gradlew` с JDK 21.

`bootJar` создаёт `build/libs/payment-core.jar`. Docker-сборка выполняет bootJar, но не тесты; перед её использованием нужно выполнить `test` или `build`.

Тесты интерфейса выполняются из `web/`:

```powershell
npm test
npm exec playwright -- install chromium
npm run test:e2e
```

Браузерные тесты сами запускают `browserTestServer` на 127.0.0.1:18080 с отдельным PostgreSQL Testcontainer и временными пользователями. Нужны JDK 21 и Docker, порт 18080 должен быть свободен. Проверяются пользовательские и административные сценарии, мобильная ширина и потеря ответа после фактического списания с безопасным повтором после перезагрузки. Это тестовые учётные записи; в обычном приложении они не создаются. Playwright завершает сервер после прогона; trace ошибки находится в `web/test-results/`.

## Профили и миграции

Профиль выбирается явно через SPRING_PROFILES_ACTIVE. `local` читает `.env`; `test` доступен только в тестовых ресурсах и использует Testcontainers. Серверный Compose передаёт URL и имя роли через SPRING_DATASOURCE_*, пароль читает из Docker secret через configtree. При самостоятельном запуске можно передать SPRING_DATASOURCE_PASSWORD через окружение. Серверный профиль включает Secure-cookie и структурированные журналы, отключает Swagger и доверяет forwarding-заголовкам только от настроенного адреса Caddy. Команды `--migrate-only` и `--reconcile-only` выполняют обслуживание без HTTP-сервера и возвращают ненулевой код при ошибке.

Схемой управляет только Flyway, миграции находятся в `src/main/resources/db/migration`. Применённые миграции не редактировать: изменения добавляются следующей версией. Readiness учитывает доступность БД; liveness от БД не зависит. Доступны только health endpoints без подробностей подключения.
